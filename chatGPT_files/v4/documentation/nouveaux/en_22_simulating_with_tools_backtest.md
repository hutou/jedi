# Simulating a scale with tools backtest

## A fixed scale on a history

`backtest` reads a security's quotations and simulates operations proposed by a fixed scale. It uses an in-memory simulation database: it adds no trade to your portfolio and does not update market quotations.

The first opening uses the **Open** price of the first selected session where sizing permits the purchase. After complete liquidation, a new opening is attempted on the following session. The report may therefore aggregate several successive trades on the same security.

From the supplied fictional file:

~~~console
jedidemo tools backtest cotations_EXA.txt \
  --scale="kc:1.23,1.14,0.88,0.76,ki:0%,kb:1,kd:0.2"
~~~

From the Demo database prepared in chapter 10:

~~~console
jedidemo tools backtest --database=demo --security=EXA \
  --scale="kc:1.23,1.14,0.88,0.76,ki:0%,kb:1,kd:0.2"
~~~

`--scale` accepts a definition or the name of a scale already recorded in that environment. Remove the `I:` or `II:` prefix shown by `score` before passing it. Here the constructor produces a type I scale whose operational definition appears in the report.

## Choose dates

Without an explicit selection, `backtest` uses **all available history**. It does not automatically reuse `score`'s 750-session window.

~~~console
jedidemo tools backtest cotations_EXA.txt --select=l750 \
  --scale="kc:1.23,1.14,0.88,0.76,ki:0%,kb:1,kd:0.2"
~~~

`--date` and `--select` follow [chapter 21's rules](en_21_preparing_a_historical_study.md#isolate-a-year-correctly). The selected start changes the opening price and mechanical starting point. A test starting with a new trade on 1 January does not automatically continue a trade begun the previous year.

## Two sizing modes

Without `--capital`, each opening requests a **fixed amount**, calculated from configuration:

~~~text
amount = integer part of
         simulation.capital × simulation.risk_rate / simulation.distance
~~~

Default settings give `20000 × 0.015 / 0.2 = €1500`. The integer quantity actually bought may leave a small fraction unused. `--distance` changes this calculation; it does not mean the `n` step count in `money`.

Adding `--money` without `--capital` adds trade protections while retaining fixed-amount sizing.

With **`--capital`**, Jedi also requires **`--money`** and calculates the quantity at each opening from risk, the capital ceiling and operability requirements:

~~~console
jedidemo tools backtest cotations_EXA.txt \
  --scale="kc:1.23,1.14,0.88,0.76,ki:0%,kb:1,kd:0.2" \
  --capital=20000 --money="r:1.5%,o:1,n:2"
~~~

[Chapter 18](en_18_capital_risk_and_position_sizing.md) explains `r`, `o` and `n`. By default this mode requires at least **two shares per checked order** and examines **three upward steps**. `--minimum-quantity` and `--operability-steps` change these checks and require `--capital` mode.

An inoperable opening is postponed to the next session and counted in the report. `--distance` cannot be combined with `--capital`. The supplied capital remains the sizing reference: the backtest does not simulate simultaneous funding of a multi-security portfolio or automatically reinvest gains through increased capital. Use `candidate` to examine funding for an actual project with your portfolio's reserves.

## Know the execution assumptions

Normal operation uses **`--execution=conservative`** and **`--opening-day-orders=next`**. Orders generated by the initial purchase become active on the next session. The engine retains **at most one proposed operation per session**, in addition to the opening when it occurs; it does not execute every step that a day might cross.

Daily data provide Open, High, Low and Close, without revealing movement order between opening and closing. Jedi therefore applies explicit rules:

1. An order already executable at the opening price takes priority over an order only touched later in the session.
2. When several orders remain possible without known chronology, the policy chooses by order type. It generally prioritises protection, then the downward purchase, then the upward sale. For loss protection not yet crossed at the opening, the downward purchase may precede protection; gain protection takes priority over that purchase.
3. The opening price applies when a gap makes the order immediately executable; otherwise the order level applies.

| Active order | Level | Open | Simulated price |
|---|---:|---:|---:|
| Limit purchase | €8 | €7 | €7 |
| Limit sale | €12 | €13 | €13 |
| StopLoss sale | €6 | €4 | €4 |
| Stop purchase | €12 | €13 | €13 |

A favourable gap can improve a Limit price; an adverse gap can exceed the Stop level and intended risk. `conservative` names this convention without guaranteeing the worst possible intraday path.

The simulation does not reconstruct the order book, partial fills or spread. Daily volume does not automatically cap executed quantities. Fees come from configuration; simulated prices do not replace actual tick rules and broker conditions.

`--execution=legacy` and `--opening-day-orders=same` remain available for specific investigations. `legacy` changes priorities and uses theoretical levels instead of gap prices. `same` permits orders on the opening day. State these explicitly in any comparison using them.

## Read the compact report first

The first command in this chapter, using EXA's 851 sessions, produces:

~~~text
History: 2023-06-30 → 2026-10-02 (851 sessions)
Requested amount per opening: 1500.00 €
Openings: 1; inoperable attempts: 0
First purchase: 2023-06-30, 150 shares for 1500.00 €
Operations including openings: 25
Cumulative gross gain: 647.11 €
Total fees: 19.14 €
Cumulative net gain: 627.97 €
Maximum investment excluding fees: 1500.00 €
Net gain / maximum investment: 41.86%
Shares held at the end: 122; value 1578.97 €
~~~

Gross gain adds sales, subtracts purchases and adds remaining shares valued at the last close. Net gain deducts fees. Maximum investment is the largest of the individual trades’ peaks of purchases minus sales, excluding fees. Backtest trades run sequentially without overlap, so the global maximum must occur in at least one trade.

The 41.86% covers the whole period; it is not an annual rate. The final €1,578.97 value is part of the gain, not another gain to add to €627.97. The 122 shares are not artificially sold at the end: the report charges no final liquidation that did not occur.

## Understand the maximum when a trade reopens

Another invented example illustrates the calculation: the first trade buys 100 shares at €10 and sells all of them at €8.50. Its gross loss is €150. The next trade buys 100 shares at €10 again.

| Trade | Peak investment before fees | State |
|---|---:|---|
| Trade_01 | €1,000 | Closed, with a €150 gross loss. |
| Trade_02 | €1,000 | Opened after the previous trade closed. |
| Backtest maximum | **€1,000** | The larger of the two peaks. |

Cumulative purchases minus sales then total €1,150: the €150 loss remains in the financial balance. This balance is used to calculate cumulative gain; it is not an individual trade’s maximum. Detailed and technical reports label it the **buy-sell balance**. It can exceed the maximum, particularly after an earlier loss.

The financial table requested with `-c f` now follows **trade creation order**, first to last. Compact summary r, the technical summary and the f total use the same maximum. Returns and ratios based on that maximum are recalculated using this value.

## Examine operations and gaps

~~~console
jedidemo tools backtest cotations_EXA.txt \
  --scale="kc:1.23,1.14,0.88,0.76,ki:0%,kb:1,kd:0.2" -c rfo
~~~

`r` retains the report, `f` adds financial results and `o` operations. `t` lists trades, `d` remaining active orders and `p` the chart. Detailed outputs may be wide: inspect them in the terminal or save them to a file. `play` column selectors are not `backtest` options.

The small `cotations_GAP.txt` file checks a loss beyond intended risk:

~~~console
jedidemo tools backtest cotations_GAP.txt \
  --scale="kc:1.4,1.2,0.8,0.6,ks:0.8,1.2,ki:10%,kb:1" \
  --capital=20000 --money="r:2.5%,o:1,n:2" -c ro
~~~

Jedi buys 125 shares at €10, then executes protection at the next opening at €4 despite its €6 level. Nominal risk of €500 becomes a €750 gross loss and a €756.13 net loss after fees. This fictional two-session path explains a rule; it is not a return study.

## Compare fixed scenarios

Changing only the scale on the same data with identical options makes a readable comparison. For example:

~~~console
jedidemo tools backtest cotations_EXA.txt \
  --scale="vr:5%,np:2,nn:2,ki:0%,kb:1,kd:0.0"
~~~

Keep losing scenarios and the assumptions explaining them too. `--display=technical` adds detailed compatibility diagnostics; the compact report provides the initial economic reading. [Chapter 24](en_24_interpreting_comparing_and_monitoring.md) organises interpretation across scenarios.
